# 架构设计

本文描述 `new-school-sdk` 当前仓库（`school-sdk` v1.8.1）的整体结构、模块职责、关键流程与已知约束，供二次开发与贡献者参考。

## 1. 定位与边界

SDK 面向**新版正方教务系统（ZFSoft）**，通过模拟浏览器行为完成登录并抓取业务数据。它不是官方 API 客户端，全部能力建立在对教务系统 Web 页面与 AJAX 接口的逆向之上。

**做什么**

- 账号密码登录，自带滑块验证码与图形验证码的自动识别
- Cookie 登录（适用于已有会话、或验证码链路无法自动化的场景）
- 课表、成绩、个人信息三类标准数据的抓取与字段翻译
- 通过 `proxy_request` 复用已登录会话，让调用方自行实现 SDK 未封装的业务

**不做什么**

- 不做写操作封装（选课、评教等）
- 不保证跨版本的正方部署完全兼容，仅通过端点表与参数覆盖提供适配能力
- 不做会话持久化（`school_sdk/session/` 仍是空壳）

## 2. 分层结构

```
┌─────────────────────────────────────────────────────────┐
│ 门面层  SchoolClient  ──factory──▶  UserClient          │
│         学校级配置                   用户级会话 + 公开 API │
├─────────────────────────────────────────────────────────┤
│ 业务层  ZFLogin │ Schedule │ Score │ Info │ ScheduleClass│
│         登录编排  课表      成绩    信息    班级课表(WIP) │
├─────────────────────────────────────────────────────────┤
│ 解析层  ScheduleParse │ 各业务类内的 _parse              │
│         节次/周次/配色    JSON 键名翻译、HTML 选择器抽取  │
├─────────────────────────────────────────────────────────┤
│ HTTP 层 BaseUserClient │ BaseCrawler                    │
│         共享同一个 requests.Session，自动拼接 BASE_URL   │
├─────────────────────────────────────────────────────────┤
│ 支撑层  PyRsa（纯 Python RSA） │ check_code（验证码识别） │
│         config.URL_ENDPOINT    │ exceptions │ utils      │
└─────────────────────────────────────────────────────────┘
```

## 3. 目录与模块职责

| 路径 | 职责 |
| --- | --- |

| `school_sdk/client/exceptions.py` | `SchoolException` → `LoginException`；`RTKException` |

| `school_sdk/client/api/__init__.py` | `BaseCrawler`：业务爬虫共享的 HTTP 层与学期映射表 |
| `school_sdk/client/api/login.py` | `ZFLogin`：完整登录编排，含两类验证码分支 |

| `school_sdk/client/api/score.py` | `Score`：成绩抓取与字段翻译 |
| `school_sdk/client/api/user_info.py` | `Info`：个人信息，基于 CSS 选择器解析 HTML |
| `school_sdk/client/api/class_schedule.py` | `ScheduleClass`：班级课表，**WIP**，仍有硬编码班级参数 |

外围：`docs/`（mkdocs-material 文档站）、`examples/`（可运行示例）、`test/test.py`（真机联调脚本，被 `.gitignore` 忽略）、`tests/test_offline_smoke.py`（离线冒烟测试）。

## 4. 两层客户端模型

```py
SchoolClient(host, port, ssl, exist_verify, captcha_type, retry, url_endpoints)
    └── user_login(account, password) ──▶ UserClient
                                              ├── get_schedule(year, term)
                                              ├── get_score(year, term)
                                              ├── get_info()
                                              ├── check_session()
                                              └── proxy_request(method, path)
```

- **`SchoolClient` 无状态、可复用**：只持有学校级配置（地址、是否有验证码、验证码类型、重试次数、端点表），一个实例可为多个用户签发会话。
- **`UserClient` 有状态**：持有 `requests.Session`、账号密码、以及 `Schedule`/`Score`/`Info` 三个**惰性创建并缓存**的业务对象。首次调用 `get_xxx` 时才实例化对应业务类。
- **两条 Cookie 登录入口**：`SchoolClient.user_login_with_cookies(cookies)` 与 `UserClient.get_dev_user(cookies)`。因缺少密码，这类会话无法自动重登，过期需调用方自行处理。

## 5. HTTP 层设计

`BaseUserClient`（门面用）与 `BaseCrawler`（业务爬虫用）各自实现了一套 `_request/get/post`，行为一致：

- 传入以 `http://`/`https://` 开头的字符串按完整 URL 处理，否则自动拼接 `BASE_URL`
- 两者**共享同一个 `requests.Session` 对象**（`BaseCrawler.__init__` 从 `user_client._http` 取），从而共享 Cookie
- 默认请求头在 `BaseUserClient.__init__` 中设置（UA + `application/x-www-form-urlencoded`）；`generate_headers()` 另可用 `fake_headers` 生成随机浏览器头

!!! note "会话重建的约定"
    `check_session()` 在检测到会话失效后会重新登录，并把新 Session 回写到 `self._http`。由于 `BaseCrawler` 在构造时拷贝了 Session 引用，**已创建的业务对象仍指向旧 Session**。因此重登录后应重建业务对象（或让 `UserClient` 重新惰性创建）。

## 6. 登录流程

```
get_login()
  │
  ├─ 1. GET  LOGIN.INDEX          → 解析 #csrftoken，获得初始 Cookie
  ├─ 2. GET  LOGIN.PUBLIC_KEY     → 取 modulus / exponent
  ├─ 3. 验证码分支（exist_verify 为 True 时）
  │     ├─ captcha_type 以 "cap" 开头 → 滑块
  │     │     ├─ GET  zfcaptchaLogin?type=resource  → 正则抠出 rtk
  │     │     ├─ GET  zfcaptchaLogin?type=refresh   → imtk / si
  │     │     ├─ GET  zfcaptchaLogin?type=image     → 缺口图
  │     │     ├─ 像素列扫描求缺口 (x, y)
  │     │     ├─ 匀加速/减速模型生成鼠标轨迹
  │     │     └─ POST zfcaptchaLogin?type=verify    → 校验，失败按 retry 重试
  │     └─ captcha_type 以 "kap" 开头 → 图形
  │           ├─ GET  kaptcha  → 验证码图片
  │           ├─ CNN 推理出 6 位字符
  │           └─ 带 yzm 提交登录，失败按 retry 重试
  └─ 4. POST LOGIN.INDEX  data={csrftoken, yhm, mm}
             mm = base64(RSA(password))   ← PyRsa 与前端 jsbn 同构
```

登录成功判定在 `_is_login(html)`：命中 `value="{account}"` 或页面含「请」字视为成功；否则读取 `#tips` 的提示文本，含「验证码」则返回 `False` 触发重试，其余抛 `LoginException`。这是基于页面特征的启发式判断，属于已知脆弱点。

## 7. 验证码识别

| 类型 | 常量 | 实现 | 依赖 |
| --- | --- | --- | --- |
| 滑块 | `CAPTCHA = "captcha"` | `check_code/type.py:captcha_func`，灰度化后逐列比较相邻像素亮度，找到连续 50 行满足条件的列即缺口 | Pillow |
| 图形 | `KCAPTCHA = "kap"` | `check_code/predict.py`，3 层卷积 CNN 一次性输出 6 个字符位的分类结果 | PyTorch、torchvision、`model.pkl`（约 39 MB，随包分发） |

`ZFCaptchaDistinguish` 是两者的统一包装，识别策略以回调函数形式注入（`verify_func`）。字符集见 `captcha_setting.py`：数字 + 大小写字母共 62 类，固定 6 位，输入图像 200×50。

!!! warning "依赖体量"
    `torch` / `torchvision` 当前是**硬依赖**且锁定 `<2`。即使只用无验证码或滑块验证码的学校，安装时也会拉入完整 PyTorch。`predict.py` 已做惰性导入（仅在图形验证码分支触发），因此后续可将其收敛为 optional extra。

## 8. 数据抓取与解析

三类业务的通用模式：**请求 → 缓存原始响应 → 键名翻译成语义化字段**。

### 课表

- 抓取：`POST SCHEDULE.API`，`gnmkdm=N2151`，body 带 `xnm`（学年）、`xqm`（学期编码）、`kzlx=ck`
- 缓存：`Schedule` 记住最近一次的 `year`/`term`，`get_schedule_dict` 发现请求的学年学期变化时自动重新加载
- 解析（`ScheduleParse`）：
    - **节次 → 时间**：`jcs`（如 `1-2`）经作息表映射为 `{"start": [8,30], "last": [9,20]}`。注意 `last` 是**末节的上课时间**而非下课时间。内置作息表可由 `get_schedule(schedule_time=...)` 或 `set_schedule_time()` 覆盖，因各校作息不同；若自定义表缺少某节次，会抛出提示补全 `schedule_time` 的 `KeyError`。
    - **周次展开**：`zcd`（如 `1-16(单)`、`3,5-8`）展开为具体周数列表，支持单双周步进
    - **配色**：同名课程复用同色，新课程按「星期 × 3 + 起始节次 + 1) % 5」在 5 色中取值

### 成绩

`POST SCORE.API`，`gnmkdm=N305005`，`doType=query`，单页取 500 条。输出同时提供 `score_list`（列表）与 `score_dict`（以课程名为键）。字段翻译如 `kcmc→course_name`、`cj→exam_result`、`bfzcj→exam_score`、`jd→grade_point`。

### 个人信息

`GET INFO.API`，`gnmkdm=N100801`，返回 HTML，用 pyquery 按固定 CSS 选择器（如 `#col_bh_id > p`）抽取学号、姓名、院系、班级、年级、专业等。这是三类数据中**最依赖页面结构**的一处，教务系统改版时优先检查此处。

## 9. 跨校适配机制

SDK 声称的"跨校可用"由三件事支撑：

1. **端点表可覆盖**：`SchoolClient(url_endpoints=...)` 可整体替换 `URL_ENDPOINT`，适配不同 URL 前缀的部署
2. **学期编码映射**：`BaseCrawler.TERM = {1: 3, 2: 12, 3: 16}`，把人类可读的学期号转成正方内部编码
3. **逃生口**：`UserClient.proxy_request(method, url_or_endpoint, **kwargs)` 复用已登录会话，kwargs 透传给 `requests`，调用方自行解析响应

此外 `exist_verify`、`captcha_type`、`retry`、`schedule_time` 都是按校差异的配置位。

## 10. 异常体系

```
Exception
 └── SchoolException(name, school_code, errmsg)   # __str__ 仅输出 errmsg
      └── LoginException                          # 登录失败、会话失效
ValueError
 └── RTKException                                 # 滑块 rtk 解析失败
```

调用方还应预期两类原生异常：缺少必要参数时的 `ValueError`（如未指定学年）、作息表缺节次时的 `KeyError`。

## 11. 工程现状

- **构建**：setuptools，`pyproject.toml` 单一配置源；`model.pkl` 通过 `package-data` 打包
- **依赖管理**：uv（`uv.lock` 已提交）；dev 组仅 `autopep8`
- **CI**：`.github/workflows/ci.yml` 仅做文档发布（mkdocs gh-deploy），**不跑测试、不做构建校验**
- **测试**：`test/test.py` 需 `.env`（`SCHOOL_HOST`/`SCHOOL_ACCOUNT`/`SCHOOL_PASSWORD`）连真实教务系统；`tests/test_offline_smoke.py` 用 mock 响应覆盖课表、成绩、会话失效、Cookie 解析等路径，无需网络，可用 `python tests/test_offline_smoke.py` 或 pytest 运行
- **注意**：`.gitignore` 中的 `test/*`、`*.json`、`test.py` 规则会忽略 `test/` 目录下的全部内容，新增可提交的测试请放在 `tests/`
- **代码风格**：`autopep8 --in-place --recursive school_sdk/`
- **提交规范**：所有提交需 DCO 签名，使用 `git commit -s`

## 12. 已知约束与改进方向

**已知脆弱点**

- 登录成功判定依赖页面含「请」字等特征，教务系统改版即失效
- `user_is_login` 在会话失效时统一返回 `False`，丢弃了 `#tips` 中的原始错误文本
- `Info._parse` 的 CSS 选择器与页面 DOM 强耦合
- `BaseCrawler` 拷贝 Session 引用，重登录后旧业务对象不会自动跟随新会话
- `self.t` 时间戳在对象构造时固定，长生命周期会话中一直是旧值

**待清理**

- `BaseUserClient` 与 `BaseCrawler` 的 HTTP 层重复，可合并为单一基类
- `ScheduleClass` 仍硬编码 `njdm_id`/`zyh_id`/`bh_id`，需从个人信息推导后才能通用
- `CheckSession`、`RedisStorage` 为空壳
- `config.py` 中 `SCORE_URL`、`INFO_URL` 是空字符串残留
- `SchoolClient` 的 `timeout`、`lan_host`、`lan_port`、`login_url_path` 写入配置后无任何代码读取
- 学期编码的兜底值不一致：课表 `TERM.get(term, 1)`，成绩 `TERM.get(term, 3)`

**建议演进顺序**

1. 把 `torch`/`torchvision` 收敛为 optional extra（如 `school-sdk[kaptcha]`），大幅降低默认安装体积。当前 `torch<2` 在 Apple Silicon + Python ≥3.10 上没有可用 wheel，`uv sync` 会直接失败
2. 为离线测试补齐更多 fixture，并在 CI 中运行，让 CI 具备回归能力
3. 抽出统一的会话管理（配合 `session/` 的持久化设计），解决重登录后的 Session 传播问题
4. 把页面特征判断集中到单一模块，降低教务系统改版时的修改面
